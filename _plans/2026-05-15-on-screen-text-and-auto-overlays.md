# On-Screen Text Baked Into AI Image + Auto-Sourced Overlays

**Date:** 2026-05-15
**Project:** youtubestudio-live → Production Doc
**Stakeholder requirement:** Two creative-quality improvements asked for in the same turn — (1) bake on-screen text directly into AI-generated stills, (2) automatically source and composite real-image overlays for rows that have `overlay_stock_terms`.

## Goals

1. The still image for a row visibly contains the row's `on_screen_text` as a designed typographic element of the scene — not a post-render lower-third.
2. Rows with `overlay_stock_terms` automatically have a real-world image sourced, cleaned up, and composited at a deliberate position in the final video, with motion that integrates the overlay into the scene.

## Constraints

- AI image generation already routes through Kie.ai with the user-picked model (Grok Imagine, Flux 2 Pro/Flex, NanoBanana, GPT Image 2). Text-rendering fidelity varies model-to-model; we must give the model a prompt that maximises legibility.
- The production doc itself is generated by an LLM and is the only place where global scene composition can be planned coherently. Layout decisions live there, not in a post-hoc heuristic.
- Real-image overlays (logos, brand marks, real-world screenshots) cannot be generated by image models — they must be sourced from the web, then cleaned up.
- Cost budget: per-overlay cost must stay under $0.05 to keep a 15-row doc reasonable. Targeting ~$0.008/overlay (~$0.032 per doc).

## Approach

### Phase A — On-screen text baked into the still

Server-side prompt augmentation in [src/app/api/generate/production-doc/image/route.ts](../src/app/api/generate/production-doc/image/route.ts).
The route currently sends `prompt` raw to Kie. New optional fields `onScreenText` (string) and `styleSuffix` (string — to pull the style's typography hint) are accepted. When `onScreenText` is non-empty, the route appends a directive of the form:

> Render the title text "<on_screen_text>" as a designed typographic element integrated into the composition — legible, balanced, in a typeface and weight that matches the illustration style. Place it where the AI prompt's negative space accommodates it. Do not letter-space awkwardly; treat the text as part of the artwork.

Client ([src/app/(app)/production-doc/page.tsx](../src/app/(app)/production-doc/page.tsx) → `generateImageForRow`) sends the row's `on_screen_text` and the active style preset alongside the prompt. No new env vars, no new dependencies. Single-route change.

### Phase B — Doc-generator plans overlay layout

Schema extension on the LLM-produced row:

```ts
interface ProductionRow {
  // ... existing fields
  overlay_stock_terms?: string;
  overlay_zone?: 'top-left' | 'top-right' | 'bottom-left' | 'bottom-right'
              | 'center-top' | 'center-bottom' | 'left-center' | 'right-center';
  overlay_size?: 'small' | 'medium' | 'large';   // ~12% / ~18% / ~25% of frame width
}
```

Updates required:

- [src/app/(app)/production-doc/page.tsx](../src/app/(app)/production-doc/page.tsx) — extend the `ProductionRow` interface.
- [src/lib/prompts.ts](../src/lib/prompts.ts) `productionDocPrompt` — when `allowOverlay` is true, instruct the LLM to (a) emit `overlay_zone` + `overlay_size` whenever `overlay_stock_terms` is non-empty, (b) write the `ai_image_prompt` so that the chosen zone is left as deliberate negative space ("leave the upper-right quadrant clean, uncluttered, with low-contrast background, ready to receive a graphic overlay").
- Schema example block in the prompt is updated so the LLM sees the new fields.
- Parsing path is forgiving — missing zone/size falls back to `top-right` / `medium`.

### Phase C — Overlay fetch pipeline (`/api/overlay/fetch`)

New POST route. Body: `{ overlayStockTerms: string }`. Returns `{ overlayUrl: string }` hosted on the workspace's R2 bucket.

Pipeline:

1. **Smart query rewriting.** If the term contains "logo" → append `transparent png`. If it contains "screenshot" → append `high resolution`. If it contains "photo" → append `clean background`. The first comma-separated term is the primary; additional terms are noise-tolerance for the search.
2. **Brave Search (Images) API call** — `https://api.search.brave.com/res/v1/images/search?q=<query>&safesearch=strict&count=10`. Filter to results with width >= 400px; rank by image type (PNG > JPG).
3. **Download** the top result via fetch with a 5s timeout, max 5MB body cap.
4. **Background removal** via Replicate `briaai/RMBG-2.0`. Skip RMBG when the source URL ends in `.svg` (already vector) or when the source was filtered to "transparent" PNGs and the alpha channel sampling on the corners shows >95% transparency.
5. **R2 upload** to `overlays/<workspace_id>/<sha256-of-input-terms>.png` so identical terms across docs reuse the same fetch (idempotent cache).
6. **Return** the R2 URL. Persist on the row as `overlay_image_url` (new field on `ProductionRow`).

New env vars (added to `.env.example` with comments — never committed live):
- `BRAVE_SEARCH_API_KEY` — Brave Search image API key
- `REPLICATE_API_TOKEN` — already exists for other features? Need to verify

Error handling — if Brave returns no result or RMBG fails, the route returns 200 with `{ overlayUrl: null, reason: "..." }` so the caller can fall back gracefully (no overlay rendered, but the still still works).

UI trigger: auto-fetch happens when the row's AI image generation completes successfully, as a fire-and-forget secondary call. Failures are silent — the overlay just doesn't show, the user can manually retry via a per-row Retry button on the overlay cell (small follow-up; not in initial scope).

### Phase D — Remotion overlay rendering

[src/remotion/utils.ts](../src/remotion/utils.ts) — extend `VideoShot` with `overlay?: { url: string; zone: OverlayZone; size: OverlaySize }`. Map from the row's `overlay_image_url`, `overlay_zone`, `overlay_size`.

Scene component — when `overlay` is present, render an `<Img>` positioned via a zone-to-coordinates lookup table, scaled per `overlay_size`, with:

- `interpolate` on opacity: 0 → 1 over 12 frames (200ms @ 60fps).
- `spring` on scale: 0.92 → 1.0 with `damping: 16, stiffness: 120`.
- Drop shadow via CSS `filter: drop-shadow(0 4px 16px rgba(0,0,0,0.35))`.
- The overlay starts ~150ms after the scene's Ken Burns starts (so the eye lands on the main composition first, then the overlay confirms).

## Security / safety

- Brave key + Replicate token are server-only, never exposed to the client.
- Downloaded images go through `fetch` with size cap (5 MB) + timeout (5 s) + content-type whitelist (`image/png`, `image/jpeg`, `image/webp`, `image/svg+xml`). Reject anything else.
- R2 keys namespaced by `workspace_id` so one workspace can't read another's overlays.
- The cache key is hash-of-input-terms, not raw input — avoids leaking workspace prompts via filename inspection.
- No PII in overlay search terms (they're brand names and visual hints), but rate-limit the fetch route at 30/min/workspace to prevent runaway loops.

## Phasing strategy

- Ship **Phase A** first — small, no new dependencies, immediate visible win.
- Then ship **Phase B** — schema-only change, no runtime cost.
- Then ship **Phase C + D** together — overlay pipeline is only useful when both fetch and render exist.

## Rejected alternatives

- **Generate overlays as part of the AI image prompt.** Doesn't work for real brands — model invents fake logos.
- **Vision-model-driven positioning at composite time.** Would cost ~$0.01 per row in GPT-4o calls and adds latency. The LLM that plans the doc already has full scene context and can decide positioning during planning at no added cost.
- **Manual upload of overlay assets.** Loses the entire automation goal.
- **`remove.bg` API for background removal.** $0.20 per image. 40× more expensive than Replicate RMBG. Same quality.

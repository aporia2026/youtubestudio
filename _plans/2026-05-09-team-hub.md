# Team Hub — owner-side cockpit for managing every team member in one place

**Date:** 2026-05-09
**Branch:** to be cut from `phase-1-foundation`
**Status:** Approved (user picked Option A three-pane layout, Mix composition, Both POV preview + per-action escalation, all four roles in scope)

## Goal

Give the owner one place to manage every team member (narrator, video editor, reviewer/client, channel editor) without jumping between `/team`, `/narrators`, `/messages`, `/projects/[id]`, the various `/[role]/[token]` portals, and the per-version review pages. The hub makes per-person workload obvious at a glance, surfaces every task regardless of status, and lets the owner act on every relevant feature inline.

The team-member-facing portals (`/narrate/[token]`, `/narrator/[token]`, `/editor/[token]`, `/editor/[token]/[projectId]`, `/review/[token]`, `/inbox/[token]`) are unchanged. Each team member still gets their own personal dashboard URL. The hub is owner-side only.

## Non-goals

- No changes to the team-member portals themselves. Their URLs, layouts, and behaviour stay exactly as they are.
- No changes to the underlying assignment data model (`narrator_assignments`, `editor_assignments`, `review_projects`, `review_versions`, `channel_editors`, `messages`, `narration_take_comments`, `review_comments`, `narrator_comments`).
- No new role types. The four existing collaborator roles plus channel_editor cover v1.
- No new chat data model. The `messages` table stays the home for 1:1 owner-collaborator chat.
- No bulk reassignment / drag-and-drop of work between team members. Considered as Option C in design alignment and rejected.
- No mobile-first design. The hub is owner-side and desktop work; mobile collapses to a drawer stack but is not the primary target.

## User-aligned decisions (locked before plan write)

1. **Location.** Replace `/team` with the new hub at `/team-hub`. The current collaborator CRUD (color, specialties, notes, role assignment, revoke access) is folded into the hub's per-person Settings tab plus a "+ Add person" button on the left rail. `/team` becomes a 308 redirect to `/team-hub`.
2. **Composition.** Mix: embed heavy editors (script editor, take-comments thread, review video player, EditorTab) as side panels; rebuild lightweight actions (status change, deadline edit, quick reply, send link, revoke access) as inline controls in the middle pane.
3. **POV mode.** Both: read-only preview of the team member's portal as the default in a "Their view" tab, plus an explicit "Act as them" escalation at the per-action level (per-comment, per-take, per-version) that adds a banner inside that surface and writes a `done by owner on behalf of <name>` audit line.
4. **Scope.** All four roles in v1: narrator, video editor, reviewer/client, channel editor.

## Approach (Option A — three-pane workspace)

### Shell layout

A persistent three-pane shell at `/team-hub`:

- **Left rail** (~280px, sticky, full height) — searchable roster of every collaborator + every channel_editor. Grouped by role: Narrators, Video editors, Reviewers/clients, Channel editors. Each row: name, color dot, role chip(s), 2–3 ambient counters surfaced from the existing `getTeamOverview` helper plus new per-role counts (`takes_pending_owner_review`, `unresolved_review_comments`, `overdue_assignments`, `idle_days`). Filter chips at the top of the rail: All / Has unread / Overdue / Idle 7d+. Search filters the visible rows.
- **Middle pane** (flex-1) — the selected person's command center. Top tabs: **Tasks** (default), **Their view**, **Activity**, **Settings**. Underneath the tab strip is a compact header: avatar + name + role chips + last-access pill + "Open their personal portal" link (opens the real `/[role]/[token]` URL in a new tab so the owner can copy-share or sanity-check end-to-end).
- **Right pane** (slides in from the right at 60–70% viewport width, dismissible) — mounts the heavy embedded components on demand. Animated via Framer Motion, same easing the existing dashboard uses. Closing the pane returns the user to the middle pane without touching tab state.

URL contract: `/team-hub?person=<collaborator_id>&tab=<tab>&surface=<surface_descriptor>`. `surface_descriptor` examples: `script:<projectId>`, `takes:<takeId>`, `review:<versionId>`, `editor-tab:<projectId>`. Deep-linkable, shareable, browser-back works correctly.

### Per-role command center contents (Tasks tab)

Each role has a templated Tasks tab. The shape is consistent across roles to keep the design coherent; the rows differ.

**Narrator command center**

Rows: one per `narrator_assignment` for this collaborator (any status). Per row: project title (links to `/projects/[id]`), status badge (`assigned|received|recording|submitted|revisions|approved|completed`), deadline pill, sections progress (e.g. "5/8 approved · 1 awaiting your review"), last-access age, share token URL with copy button. Action strip: Open script (right pane → embedded ScriptEditor scoped to this project's script) · Open take comments (right pane → embedded TakeComments thread, picks the most recent take with unresolved comments first) · Quick chat (inline thread in middle pane) · Change status (inline select) · Edit deadline (inline date picker) · Resend invite email.

**Video editor command center**

Rows: one per `editor_assignment` for this collaborator. Per row: project title, status badge (`assigned|editing|submitted|approved|completed`), deadline, latest review version link, unresolved comment count, last-access age. Action strip: Open EditorTab (right pane → embedded `EditorTab` component for the assigned project, gives the owner everything the editor sees) · Open review session (right pane → embedded `ReviewPage` on the latest version) · Upload video on their behalf (Phase 11 owner-upload flow, opens inline) · Quick chat · Change status · Edit deadline.

**Reviewer/client command center**

Rows: one per active `review_share` granted to this collaborator. Per row: project title, share permission, last-access age, access count, expires-at, unresolved comment count from this reviewer. Action strip: Open review session as them (right pane → embedded `ReviewPage` in their permission view) · Extend expiry (inline date picker) · Revoke link (inline button with confirm) · Quick chat.

**Channel editor command center**

Rows: one per `channels.editor_assignment` (i.e. the channels they are linked to via `channel_editors`). Per row: channel name, scheduled-items count this week, last-access age. Action strip: Open schedule filtered to them (links to `/schedule?editor=<id>`, no embedded surface — the schedule UI is large enough that opening it as a side panel would feel cramped) · Quick chat · Revoke channel access.

All four templates share: an "Add assignment / link" button at the bottom of the rows that opens the existing assignment-creation flow inline (already exists in `/narrators` and on the project detail page; we reuse the components rather than duplicating).

### Their view tab (POV preview)

Embeds the team member's actual portal in an iframe, scoped to their `personal_token` or share token. Constraints:

- iframe `sandbox="allow-same-origin allow-scripts allow-forms"` (no `allow-top-navigation`).
- `pointer-events: auto` on first load so the owner can scroll/click around to inspect what the team member sees, but every state-changing action inside the iframe is gated by the existing portal's auth (the owner's session does not leak into the iframe).
- A visible "READ-ONLY PREVIEW" pill overlaid on the iframe header so the owner cannot mistake it for their own action surface.
- Channel editors don't have a dedicated portal; their POV is a filtered slice of `/schedule`. We render that slice inline in the tab rather than as an iframe.

### Per-action "Act as them" escalation

Lightweight actions in the middle pane never need impersonation; they are the owner's own administrative actions on the assignment.

Heavy actions inside embedded surfaces (posting a take comment, posting a review comment, replying in a comment thread, marking a take or version approved) get an explicit "Act as <name>" toggle next to the post button. When toggled on:

- Pre-submit confirm dialog: "This will be posted as <name>. The audit log will record that you posted on their behalf."
- The DB write goes through a new helper `actAsCollaborator(collaboratorId, fn)` that asserts the owner has access to that workspace, runs `fn()` with the collaborator's identity for the write, and inserts a `team_hub_audit_log` row capturing `(actor_user_id, target_collaborator_id, action_type, surface, target_id, performed_at)`.
- The post itself stores the collaborator id in its existing author column (so it shows up correctly in their portal), plus a new `posted_by_owner` boolean on the existing tables.

This is the only schema change in the plan.

### Settings tab (per person)

Folds in the existing `/team` CRUD: name, email, color, specialties, notes, role(s), personal token (with regenerate), revoke all access (existing big red button). For channel editors: which channels they are linked to with add/remove. For each role they hold, a section showing their portal URL with a "Copy invite link" button.

### Activity tab (per person)

Time-ordered feed of every event for this collaborator pulled from the existing tables: assignments created/updated, takes uploaded, comments posted (theirs and on their work), review versions submitted, status changes, last-access events. Powered by a new server helper `getCollaboratorActivity(collaboratorId, limit)` that does the union over the existing tables. No new persistence.

### Migration from /team

- `/team` → 308 redirect to `/team-hub`.
- The "+ Add person" CTA on the left rail opens the same modal `/team` used; reuse the component.
- The existing `/narrators` page is not removed in v1 (it has narrator-specific affordances we want to keep around while users get used to the hub) but a banner is added at the top of `/narrators` saying "Manage all team members in one place at /team-hub" with a link.
- `/messages` stays. The hub's "Quick chat" inline thread reuses the same `messages` table; opening the full inbox links to `/messages?with=<id>`.

## Embeddable-component refactor list

Each of these is a small refactor — extract the existing component so it accepts its scope via props instead of from page-level state, then mount it in the right pane.

1. **`ScriptEditor`** — currently lives inline in `/projects/[id]` and in `/generator`. Extract into `src/components/script/ScriptEditor.tsx` taking `scriptId` (and optionally `projectId`) as props. Right-pane mount at `surface=script:<projectId>`.
2. **`TakeComments`** — already a component (`src/components/narrator/TakeComments.tsx` based on the report; verify). Confirm it accepts `takeId` as a prop. Right-pane mount at `surface=takes:<takeId>`.
3. **`ReviewPage`** — currently a full page (`src/app/review/[token]/page.tsx`). Extract the inner experience into `src/components/review/ReviewSession.tsx` taking `reviewProjectId` + `versionId` as props. Right-pane mount at `surface=review:<versionId>`.
4. **`EditorTab`** — already a component (`src/components/editor/EditorTab.tsx`). Verify it accepts `projectId` as a prop without page-context dependencies. Right-pane mount at `surface=editor-tab:<projectId>`.

If any of these have hidden coupling (router state, top-level auth context, page-level effects), the refactor for that one component goes in its own commit so the diff stays reviewable.

## Schema change

One migration: **0050_team_hub_act_as_audit.sql**.

- New table `team_hub_audit_log` (workspace_id, actor_user_id, target_collaborator_id, action_type text, surface text, target_id uuid, result text check (result in ('success','failure')) not null, error_message text null, performed_at timestamptz default now(), with `(workspace_id, performed_at desc)` index for the per-workspace activity query).
- Add boolean `posted_by_owner` (default false) to: `narration_take_comments`, `review_comments`, `narrator_comments`. Backfill with `false` (free; default applies).

No row-locking changes, no constraint changes, no data backfill beyond defaults. Safe to deploy live.

## Cost and pricing implications

None. The hub is pure UI over existing data. No new AI calls, no new third-party APIs, no new hosted services. The iframe POV preview hits the existing portal routes which already authenticate via the team member's token.

If we later wire AI to this surface (e.g. "summarise this person's week for me"), that goes through the existing `generateText` + `ai_spend_log` instrumentation from Phase 6.1; it's not part of v1.

## Test plan

Unit:

- `actAsCollaborator(collaboratorId, fn)` — asserts workspace match, captures audit row, propagates `fn` errors without writing audit (or writes audit with `failed=true`? — open question, see below).
- `getCollaboratorActivity` — joins / unions over the existing tables, no N+1, returns time-ordered events with a stable shape.
- Per-role count helpers (`countTakesPendingOwnerReview`, `countUnresolvedReviewComments`, `countOverdueAssignments`, `countIdleDays`) — pure SQL helpers, tested with seeded fixtures.
- `surface_descriptor` parser — round-trips every surface type, rejects malformed strings.

Integration / manual:

- **Roster correctness:** add a narrator + editor + reviewer + channel_editor; each appears in the correct group with the correct counters.
- **Tasks per role golden path:** for each of the four roles, click into a person, see all their assignments regardless of status, click each action in the strip and confirm the right surface mounts in the right pane.
- **POV preview:** open Their view tab for a narrator with an in-progress assignment; the iframe shows their actual `/narrator/[token]` view; the READ-ONLY PREVIEW pill is visible.
- **Act as them — happy path:** with the toggle on, post a take comment as a narrator; verify the comment shows up in the narrator's portal authored as them, and a `team_hub_audit_log` row exists with the correct `(actor, target, action_type, surface, target_id)`.
- **Act as them — refusal of cross-workspace target:** call the helper with a collaborator from a different workspace; helper throws and no row is written.
- **Settings tab:** edit name + color + specialties + notes for a collaborator; confirm the existing `/team` modals and validation still apply.
- **Migration from /team:** visit `/team` and confirm 308 to `/team-hub`. Visit `/narrators` and confirm the banner.
- **Right-pane on small screen:** at 1366×768 the left rail collapses to icons-only and the right pane uses 80% width; nothing overlaps; close button is reachable.
- **Embedded ScriptEditor in right pane:** edit a script section, save, close pane, reopen — the change persists. (Same component, same backend, same persistence — but this verifies the prop-extraction refactor did not break save path.)
- **Audit log scoping:** the audit log is workspace-scoped; switching workspaces doesn't show another workspace's actions.

## Alternatives rejected

- **Option B (profile-per-person, dedicated `/team-hub/[id]` page).** Cleaner spacing per person and shareable per-person URLs, but every context switch between team members costs a click back to the index. The user explicitly said "extremely organized by team member and his position" — keeping the roster always visible serves that requirement better than per-person pages do.
- **Option C (kanban-by-person with drag-and-drop reassignment).** Beautiful at-a-glance workload view and delightful drag-to-reassign, but each role's "task" is a different DB shape, so drag dispatch is role-specific with permission checks per shape. Too much engineering risk for v1, and the card paradigm is a poor surface for the heavy actions (editing a 5,000-word script in a card is wrong). Could revisit as a v2 alternative view inside the hub if users want it.
- **Building new inline controls instead of embedding existing ones.** Considered briefly. Two implementations of the same feature drift apart over time and we maintain both. The user's "Mix" answer locked this out: heavy editors embed, lightweight actions rebuild — exactly the right split for this codebase.

## Resolved decisions (post-plan-write user answers)

1. **Audit log on failure: always write.** `actAsCollaborator(collaboratorId, fn)` writes a `team_hub_audit_log` row regardless of whether `fn` succeeds or throws. Schema gets a `result` column (`'success' | 'failure'`) and a nullable `error_message text` column. On failure the audit row is written first (best-effort, in its own transaction), then the original error is rethrown so the caller sees the same failure semantics. Rationale: the user wants every "act as them" attempt traceable, including blocked / failed ones, because intent matters even when the action did not commit.

2. **`/narrators` sunset after two weeks.** Ship the hub with a banner on `/narrators` ("Manage all team members in one place at /team-hub"). Two weeks of dogfooding is the verification window. At the end of the window we audit that the hub covers every narrator-specific action `/narrators` exposes today. If yes, delete the page and its route file in a single follow-up commit. If a gap is found, port the missing affordance into the hub first, then delete. Rationale: two parallel surfaces drift; we already locked that out at the component level via "Mix" composition and the same logic applies at the page level. The two-week window is the safety net.

3. **Channel-editor creation: hybrid (Option 3c).** The hub's left rail "+ Add person" button offers all four roles for entry-point consistency. Picking "Channel editor" opens a small modal that asks "which channel?" first, then routes into the existing channel-editor creation flow already used by `/schedule` and `/channel/[id]/brand-kit`. No new third creation surface — same backend code path, just a new entry point. The other two creation locations (`/schedule`, `/channel/[id]/brand-kit`) stay as-is so context-driven creation continues to work where it makes sense.

4. **Animation: full Framer Motion transitions.** Shell transitions (left rail filter changes, middle pane person switch, right pane slide-in/slide-out, tab switches) all use Framer Motion. No reduced-motion fallback. Use the existing easing values the dashboard uses for visual coherence.
